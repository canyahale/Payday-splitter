Payday Splitter

Set it and forget it.

Every payment landing in the agent vault is automatically split — 70% main wallet, 20% savings, 10% gas reserve — by a Reactive contract. No one watches. Nobody clicks anything.

An agent gets paid. Someone moves the money by hand. One wrong address — and the whole payment is gone. That happened to us: 11,250 IAO, sent to the wrong wallet in a single manual transfer. Payday Splitter fixes the destinations when the vault is deployed, so no one ever types an address again.

How the loop works

A payment lands. The Reactive contract sees it. The vault splits it. Nobody is watching.

1 Payment 1,000 MPT
2 Vault Base Sepolia
3 Reactive Lasna · sees the event
4 Callback split it
5 Split 700 / 200 / 100
  1. SplitterVault — Base Sepolia. It holds incoming payments and can only split when its callback() is called by the Reactive callback proxy, with the sender equal to the PaydayReactive address fixed at deploy. It cannot trigger itself — without Reactive, nothing splits.
  2. PaydayReactiveOmni — Lasna. It subscribes to Transfer(token, *, vault) events on Base Sepolia. When one fires, react() requests a callback to the vault with the token and amount.
  3. The callback delivers the split. The callback proxy on Base Sepolia calls the vault, and the vault sends 70% to the main wallet, 20% to savings, 10% to the gas reserve. The rounding remainder goes to the gas reserve. Shares and destinations are set once, at deploy — that is the point.

What broke along the way

The honest build log — the failures are part of the submission, not hidden.

  1. The first version could never run. It used Reactive's legacy pattern (vmOnly), but the RVM no longer exists on Omni, so react() reverted on entry. That contract is blacklisted with a small debt and its vault's 1,000 MPT is stranded. The port to the Omni pattern (onlySystem + SYSTEM.subscribe + requestCallbackV_1_0) fixed it.
  2. Then the callback ran out of gas. The callback needs 148,700 gas, but a 300,000 limit only delivers about 144,776 after the proxy overhead — short by 3,924. Raising the limit to 400,000 and redeploying both contracts produced the working loop.
